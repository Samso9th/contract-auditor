Contract Auditor audits a Go HTTP API and reports every place the **code**, the
**OpenAPI spec** and the **published docs** disagree.

Each finding ships with a Go test that fails against the current code. If the
test passes, the finding was wrong and gets dropped.

<Card title="Nothing reaches the report unverified" icon="shield-check" horizontal>
  That one constraint is the whole design. See [The verification
  gate](/verification-gate).
</Card>

## The problem

Three descriptions of the same API, edited by different people at different
times: the handler code, the generated spec, and the prose partners read.

Code review asks whether the code is correct, never whether it still matches what
was promised. Drift surfaces at integration time, in someone else's codebase.

## Measured on a real payments API

| Signal | Value |
|---|---|
| Endpoints in code | 841 |
| Endpoints in the published spec | 170 |
| Endpoints with no doc annotation | 500 (59%) |
| Responses typed only as "an object" | 153 of 194 (79%) |

<Warning>
  841 vs 170 is not 671 missing docs. Admin and internal endpoints belong out of
  public documentation. The real problem is that nobody knows which of the 671
  should have been published.
</Warning>
