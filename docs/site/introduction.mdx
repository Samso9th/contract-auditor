Contract Auditor audits an HTTP API and reports every place the **code**, the
**OpenAPI spec** and the **published docs** disagree.

Each finding ships with a Go test that fails against the current code. If the
test passes, the finding was wrong and gets dropped.

<Card title="Nothing reaches the report unverified" icon="shield-check" horizontal>
  Everything else in the design follows from that. See [The verification
  gate](/verification-gate).
</Card>

## The problem

An API ends up with three descriptions of itself: the handler code, the
generated spec, and the prose your partners read. Different people edit each one,
at different times.

Code review asks whether the code is correct. It does not ask whether the code
still matches what was promised, so the difference tends to show up at
integration time, in someone else's codebase.

## Measured on a real payments API

| Signal | Value |
|---|---|
| Endpoints in code | 841 |
| Endpoints in the published spec | 170 |
| Endpoints with no doc annotation | 500 (59%) |
| Responses typed only as "an object" | 153 of 194 (79%) |

<Warning>
  841 vs 170 is not 671 missing docs. Public documentation is for the API key
  holders you integrate with, so anything an API key is not meant to reach
  belongs out of it: admin, internal, and every JWT route your own UI calls on
  behalf of a signed-in user. The line is the credential, not the feature. The
  real problem is that nobody knows which of the 671 should have been published.
</Warning>

  </Card>
  <Card title="Platform and DevEx" icon="gauge">
    A number for doc drift, instead of a hunch.
  </Card>
</CardGroup>

<Note>
  The audit reads source. Stage 1 parses the route table out of the handlers,
  and the verification gate compiles and runs a test against them. So it runs
  where the code is: in the provider's repository, or in yours if the code was
  shared with you. It cannot audit an API you can only reach over the network.
</Note>
